# Changelog

All notable changes to Netjes are recorded here: the `netjes` npm package and the `Netjes` and `Netjes.Images.SkiaSharp` NuGet packages, which are released together under one version. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and versions follow [Semantic Versioning](https://semver.org/spec/v2.0.0.html). Before 1.0, a new version can change the API; its entry says what to do.

## [Unreleased]

### Added

- `<Link>`, `<Form>`, `<SubmitButton>` and `<Image>` take a `ref` to the element they render. `LinkProps`, `FormProps`, `SubmitButtonProps` and `ImageProps` now start from React's `ComponentPropsWithRef` instead of the `*HTMLAttributes` types, which left the ref out, so `<Link ref={ref}>` is no longer a type error. The ref already reached the element at runtime, and only the types refused it; an app that worked around the type error, for example with `document.getElementById(id)`, can pass the ref instead. The four types also include `key` now; React handles it, as for any element, and never passes it to the component.
- Once the client router runs in a document, `<html>` carries `data-netjes-hydrated=""`: the sign that the client router runs in the document, which end-to-end tests wait for before they click, with `await expect(page.locator('html')).toHaveAttribute('data-netjes-hydrated', '')` ([testing](docs/guides/testing.md#wait-for-hydration), [ADR 0025](docs/decisions/0025-a-mark-on-html-says-the-client-router-runs.md)). Content inside a Suspense boundary can hydrate after it. It appears after the router has registered as the page's action client, on hydrated pages and on pages rendered in the browser when no sidecar was ready, and the server never renders it. A test helper that waited for the router's key in `history.state` should wait for the attribute instead: the browser keeps that state when it loads the document again, so after a reload the key is there before any of the page's scripts has run. The name is reserved, and a stylesheet or a DOM snapshot that reads `<html>`'s attributes in the browser now sees one more.
- Testing Library works with Vitest's fake timers. Under `vi.useFakeTimers()`, `waitFor`, `findBy…` and user-event never returned, because Testing Library moves fake timers on only through Jest's `jest` global. Netjes's setup file now defines that global while Vitest's timers are fake, and leaves it undefined with real timers ([ADR 0027](docs/decisions/0027-testing-library-advances-vitest-fake-timers.md)). `waitFor` and `findBy…` move the fake clock on as they wait, and their timeout counts fake time; create user-event's user with `userEvent.setup({ advanceTimers: vi.advanceTimersByTime })`. While timers are fake, `typeof jest` is `'object'`, so a library that looks for Jest finds it then, and a test on `vi.useFakeTimers({ shouldAdvanceTime: true })` takes Testing Library's path for fake timers. A `jest` global the app's own setup file defines, or a test assigns, is kept.
- `createTestApp()` starts from the app's `netjes({ query })` defaults. `netjes()` sets Vitest's `test.provide['netjes:query']` to the `query` option's `defaultOptions` (`{}` when there are none, nothing with `query: false`), next to the app's own `provide` keys, and Netjes's setup file hands them to the harness ([ADR 0028](docs/decisions/0028-test-harness-starts-from-the-apps-query-defaults.md)).
- A route warning for an endpoint of the app that ties with a page or a page action. Such an endpoint ranks the same as the page in ASP.NET Core's matcher: it has an HTTP method in common with it, the same order, route precedence and literals, a host in common or no host on either, and accepted content types listed by both or by neither (two endpoints that both list content types tie for a request without one, such as a POST without a body). ASP.NET Core cannot choose between the two and answers each request that both match with 500 (`AmbiguousMatchException`), as it did before. Now the app also logs a warning at startup, in the category `Netjes.Routing.RouteDiagnostics`, and `netjes routes` lists it (the kind `ambiguous-endpoint` in `--json`), naming the endpoint's methods and route and the page file. Netjes's own `MapLocaleRedirect()` next to an `app/page.tsx` is one such endpoint. Give the endpoint `.WithOrder(-1)` if it should answer those URLs, or change its route. An app that keeps the tie, or whose own matcher policies tell the two endpoints apart, can raise the category's log level, which hides every route warning ([ADR 0029](docs/decisions/0029-an-endpoint-that-ties-with-a-page-is-a-route-warning.md)). The routing guide has a new section, [Endpoints next to pages](docs/guides/routing.md#endpoints-next-to-pages), on which endpoint answers a URL and how to link to a file next to a page.
- `PageRouteMetadata` and `CachedPageMetadata` in `Netjes.Routing`, so app code and tests can find the app's pages by walking `EndpointDataSource`, as `netjes routes` does ([endpoint metadata](docs/reference/csharp-api.md#endpoint-metadata)). Every endpoint that serves a page carries `PageRouteMetadata`, with the page's `Pattern` as its file names it and `IsLoader`, true on the endpoint `MapPageLoader` maps. Every endpoint `CachePage` is put on carries `CachedPageMetadata`, with the `Duration` and `Tags` it was given. Apart from `CachePage`'s copy of its tags (under Changed), this is new API only, and nothing else changes at runtime. Code that finds a page's endpoint by its display name (`Page /blog/[slug]`), which is not part of the API, can read `PageRouteMetadata` instead.
- `route()` and `buildHref` take a fourth argument, `{ hash }`, which adds a `#fragment` after the query: `route('/docs/[...path]', { path: ['guides', 'caching'] }, undefined, { hash: 'keys' })` is `/docs/guides/caching#keys`. The hash is the id of an element on the page. One leading `#` is dropped and the rest is percent-encoded (`'über-uns'` becomes `#%C3%BCber-uns`, which browsers and the router decode when they look for the element); with nothing left, no fragment is added. The third argument is still the query, so a link with a fragment and no query passes `undefined` there ([routing guide](docs/guides/routing.md#links)). The generated `route()` has a new signature, so run `npx netjes generate` after upgrading, or start the app in Development, and commit `generated/netjes.ts`: `npx netjes generate --check` in CI fails until you do. Until then `route()` keeps its old signature and takes no `hash`. A link whose fragment you write into the string yourself needs no change.
- `NetjesContentSecurityPolicy.ScriptHashes` in C# and `CSP_SCRIPT_HASHES` from `netjes` hold the `script-src` sources that allow, by their hashes, the inline scripts Netjes writes with the same text into every document, for a Content-Security-Policy without a nonce: `$"script-src 'self' {NetjesContentSecurityPolicy.ScriptHashes}; object-src 'none'; base-uri 'self'"` ([security](docs/guides/security.md#hash-based)). In this version they hold one hash, of the bootstrap that collects streamed `Page.Defer` values: `'sha256-FSjVV+FzmXP8KKrLKLdvst/5N/bEWSkde01XzpGKRgs='`, the hash the docs gave for apps to paste, unchanged since 0.0.1. An app that pasted it into its policy replaces it with the constant. Nothing changes in this version, but a pasted hash blocks the bootstrap once a Netjes version changes the script, while the constants change with it. The scripts that deliver `Page.Defer` values, and React's scripts that reveal Suspense boundaries, are still covered by no hash. Nor do the constants hold the hash of React's script for form actions that are functions, whose text follows the React version; the security guide says what a page with such an action needs.
- After a client navigation to another path or query, the router announces the new page in a visually hidden live region (`aria-live="polite"`, marked `data-netjes-route-announcer`), which it renders after the app's content once the page has hydrated. It reads the page's `document.title`, else the text of its first `h1`, else its path, and speaks only when that differs from the previous page's name. A refresh, a form post that stays on its page, a link to a fragment of the page on screen and a page that an intercepting route shows in a modal are not announced ([Focus and announcements](docs/guides/routing.md#focus-and-announcements), [ADR 0033](docs/decisions/0033-client-navigations-announce-the-page-and-start-the-focus-over.md)). The server's HTML does not change, and the region has no role, so a test's `getByRole('status')` or `getByRole('alert')` finds what it found before. Give each page a title of its own: a page whose title is the previous page's is not announced. Remove an announcer of the app's own, or each page is announced twice. An end-to-end test that reads the whole text of a container, such as `body`, now also gets the region's text: read the element it means instead.
- New apps' root layout starts with a "Skip to content" link to `<main id="content">`, the first element Tab reaches after a page load and, now that the router starts the focus over, after a client navigation. An existing app can add the same to its root layout: `<Link href="#content" prefetch="none" className="sr-only focus:not-sr-only">Skip to content</Link>` first, and `id="content"` on its `<main>`.
- Warnings when a document's Content-Security-Policy refuses what the document needs. Netjes compares each policy in the `Content-Security-Policy` header that goes out on a document, the app's own or else `NetjesOptions.ContentSecurityPolicy`, with what the document needs, and `Netjes.Rendering.PageRenderer` logs a warning for each problem, once per policy, naming the directive and what to change. Scripts follow `script-src-elem`, else `script-src`, else `default-src`, and a list there that holds the document's nonce allows them all. For any other list, Netjes warns when the list refuses the inline bootstrap (it lists neither the hashes in `NetjesContentSecurityPolicy.ScriptHashes` nor `'unsafe-inline'` without a hash, a nonce or `'strict-dynamic'` beside it), has `'strict-dynamic'`, or holds none of `'self'`, `*`, `http:`, `https:` or a host source for the module scripts; when such a list holds a nonce that is not the document's, one the app made without `HttpContext.GetCspNonce()`, the one warning for it says to take the nonce from `GetCspNonce()`. In Development it also warns when such a list leaves out the Vite dev server's origin (`http://localhost:5173` by default), when `connect-src`, or `default-src` without `connect-src`, leaves out the HMR socket (`ws://localhost:5173`, which neither `'self'` nor a nonce covers), and when the list that style elements follow (`style-src-elem`, else `style-src`, else `default-src`) holds neither the document's nonce nor `'unsafe-inline'` without a hash or nonce beside it, for the styles Netjes inlines and Vite's client adds. It does not check the images and fonts that Vite serves from its origin in Development, which a policy with `img-src`, `font-src` or `default-src` lists there ([what Netjes checks](docs/guides/security.md#what-netjes-checks), [in development](docs/guides/security.md#in-development), [ADR 0037](docs/decisions/0037-csp-kept-as-written-in-development-with-warnings.md)). The policy still goes out as written, in Development too, and nothing else changes. An app that sees such a warning changes its policy as the warning says, and in Development it can instead send the policy only outside Development; an app that sees none has nothing to do.
- `renderDocument(page, options)` and `inlineScriptHashes(html)` in `netjes/testing`. `renderDocument` renders a page's whole document as the server sends it to a crawler, the page inside its layouts with the head, Netjes's inline scripts and the payload, from what the test passes: the props, each layout's props by the layout's file, the shared props, the route values and the URL ([the document](docs/guides/testing.md#the-document), [ADR 0038](docs/decisions/0038-netjes-testing-renders-a-pages-document.md)). A Promise in the props is a `Page.Defer` value. It builds the segments that wrap the page from the pages map, by the server's rules, and leaves out what only the server adds: the build's stylesheets and scripts, development styles, the query entries a loader seeds with `.WithQuery`, metadata from C#, the antiforgery token, the locale, draft mode, the base path and the image optimiser's settings. A boundary file renders inside the layouts down to its own folder, with no route. It runs in Vitest's node environment, with the `netjes()` plugin: a test file that calls it starts with `// @vitest-environment node`, and in a DOM environment it rejects with an error that says so. `inlineScriptHashes` lists the `'sha256-…'` hashes of the inline scripts in a document that a browser runs, to compare with those a policy without a nonce lists; a crawler's document has none of the scripts React streams to reveal a Suspense boundary for a visitor, and no `<Script>` code, which the browser adds. New apps get `app/document.test.ts`, which renders the home page's document and checks that the only inline script in it is the one `CSP_SCRIPT_HASHES` lists; an existing app can copy it from the template. A test that renders a document through `netjes/server-entry`, with a payload it writes itself, can call `renderDocument` instead: that entry point and its payload stay internal and can change in any version. The plugin's `virtual:netjes/pages` module now also exports `appDir`. Apps that call neither function have nothing to change.
- `NetjesOptions.TrailingSlash` (`Netjes:TrailingSlash`) and the enum `TrailingSlash` decide whether a page's URL may end in a slash. `Ignore`, the default, answers `/about` and `/about/` alike, as before. `Never` answers a `GET` or `HEAD` for `/about/` with a 308 to `/about`, and a client navigation with a redirect payload; a catch-all's value loses its last slash (`/docs/a/b/` goes to `/docs/a/b`, so `[...path]` gets `a/b`), and `/` stays as it is, also under a base path. `/robots.txt/` and `/sitemap.xml/` go to `/robots.txt` and `/sitemap.xml` too. Only the URL the client sent is redirected, as for another case of a page's URL (below). Behind a proxy or CDN that adds a trailing slash, `Never` loops: turn off one of the two ([One URL per page](docs/guides/routing.md#one-url-per-page), [ADR 0039](docs/decisions/0039-a-page-url-has-one-spelling.md)).
- `Netjes.Href`, for a link that C# sends to one of the app's pages or to another site: `public sealed record NavLink(Href Href, string Label)`, filled with `new Href("/about")`. The generated file writes a property of that type as its `Href` schema (`Href.nullable()`, `z.array(Href)` and so on), so the props parse checks the link against the app's pages, and a component passes it to `<Link href>` without `Href.parse` or a cast ([Links from C#](docs/guides/data-loading.md#links-from-c), [ADR 0040](docs/decisions/0040-links-from-csharp-are-a-href-type.md)). The constructor throws `ArgumentException`, and `Href.TryCreate` returns false, for a URL that starts with none of `/`, `?`, `#`, `http:`, `https:`, `mailto:` and `tel:`, that starts with `//` or `/\`, that holds an ASCII control character, or that starts or ends with a space. C# checks only that shape: a root-relative `Href` that no page serves, such as `/llms.txt` or a URL that already has the base path, fails the props parse, and the page renders its nearest error boundary. The server answers that with 500 when the component that parses the link is outside every Suspense boundary; under one, such as a `loading.tsx`, it sends the boundary's fallback with the loader's status, and the error boundary renders in the browser. So a link to an endpoint or a file stays a `string`, and so does a link from a CMS, checked with `isHref` where it is rendered. JSON holds an `Href` as a plain string, written by `HrefJsonConverter`, which is public so that a source-generated `JsonSerializerContext` can use it too. Minimal APIs bind no query value, route value or header to it, `[AsParameters]` included, and form binding reads none from the field of a property's name, so a URL from the request, such as a `returnUrl`, stays a `string`. Props of type `string` are unchanged, and an app that sends no `Href` has nothing to do but regenerate: the generated file now declares `routePatterns`, `isHref()` and the `Href` schema right after its imports, before the schemas of the C# types, which may use it, and its exports are the same. Run `npx netjes generate` after upgrading, or start the app in Development, and commit `generated/netjes.ts`: `npx netjes generate --check` in CI fails until you do.
- `netjes export` warns about each loader that reads the query string: a page loader of a page it writes, or a layout loader above one. The export requests every URL without a query string, and a static host serves the file it wrote for every query string, so such a page shows what its loader returned without one, whatever the address holds: `/blog?tag=react` gets the page written for `/blog`. The page is still written and the exit code is unchanged. A loader that requires the value, through a parameter with no default value and a type that is not nullable (`int page`, or `string q` with nullable reference types on), still fails the export, as before: minimal APIs answer 400 without the value, and the pages below a layout loader that requires one fail. Its warning names the keys it requires and says that the export fails; give the parameter a default value or a nullable type to export the page without one. The warning, in the new category `Netjes.Export.QueryString`, names the file, the query string keys, and the page's route or the pages below the layout ([static export](docs/guides/static-export.md#loaders-that-read-the-query-string), [ADR 0041](docs/decisions/0041-the-export-warns-about-loaders-that-read-the-query-string.md)). A parameter counts when minimal API binding reads it from the query string, `[FromQuery]` and members of an `[AsParameters]` type included; a loader that reads `HttpContext.Request.Query` itself, or takes a type that binds itself with `BindAsync`, is not reported. To act on it, make the value a route parameter with `.StaticParams(...)` to export a page for each value, or exclude the page with `.ExcludeFromExport()` (on a layout loader, it leaves out every page below the layout). For a page meant to be exported without its query string, set `Logging:LogLevel:Netjes.Export.QueryString` to `Error`, which silences the warning for every loader. The Blog example's export now logs one, for `/blog`, whose tag filter it keeps as its example. The docs now also say that `useSearchParams()` sees no query string on an exported page, whatever the address bar shows, and show `window.location.search` read in an effect as the remedy ([in the browser](docs/guides/static-export.md#in-the-browser)).
- `APP_PORT` moves the host port of the template's Compose stacks. `APP_PORT=8090 docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d` publishes the production app on port 8090, and `APP_PORT=8090 docker compose up` publishes development on 127.0.0.1:8090; without it, both publish port 8080 as before. Compose reads it from the shell or from a `.env` file next to the Compose files. The app still listens on 8080 inside the container, and Vite's port, 5173, does not move ([Docker](docs/guides/deployment.md#docker)). An app made before this release that wants it changes `"8080:8080"` in its `docker-compose.prod.yml` to `"${APP_PORT:-8080}:8080"`, and `"127.0.0.1:8080:8080"` in its `docker-compose.override.yml` to `"127.0.0.1:${APP_PORT:-8080}:8080"`.
- `netjes export` writes `sitemap.xml` and `robots.txt` for an app that maps `MapSitemap` and `MapRobotsTxt`, requested from the app after the pages like a page. The exported sitemap lists exactly the pages the export writes, in the order it writes them, and leaves out the pages marked `.ExcludeFromSitemap()` or `.ExcludeFromExport()`; the sitemap the app serves lists the pages marked `.ExcludeFromExport()` as before. Both files take their URLs from the `siteUrl` passed to the Map calls in the Production environment, which the export runs in. To keep either file out, add `.ExcludeFromExport()` to its Map call, and to `MapRobotsTxt` as well when the sitemap is left out, since `robots.txt` names it. A check that expects the export to hold neither file must change ([static export](docs/guides/static-export.md#sitemap-and-robotstxt), [ADR 0046](docs/decisions/0046-the-export-writes-the-get-endpoints-marked-includeinexport.md)).
- `.IncludeInExport()`, a convention for any endpoint, which `netjes export` writes as a file at its URL, like a Next.js route handler with `dynamic = 'force-static'`: `app.MapGet("/llms.txt", ...).IncludeInExport()` writes `out/llms.txt`. The export requests it with a `GET` and no query string after the pages and writes the body of its 200 byte for byte, without its headers; any other status fails the export. It fails before writing anything when such an endpoint answers no `GET`, has route parameters, a path segment that is no safe file name or a last segment without a file extension, requires authorization, or has the path of a file in the client build or of another file the export writes. `.ExcludeFromExport()` wins over it. One that reads the query string is warned about in `Netjes.Export.QueryString`, as a page loader is ([static export](docs/guides/static-export.md#other-endpoints-as-files-includeinexport)).

### Changed

- `netjes()` adds a setup file of its own to every app's Vitest `setupFiles`, after the app's own setup files, also when the app sets `setupFiles` itself, `[]` included. The cleanup file (`netjes/testing/setup`) is still added only when the app sets none. An app that set `setupFiles: []` to keep Netjes's setup files out now gets the new one; `netjes({ test: false })` still leaves out every Vitest setting the plugin adds, this file included. Under Vitest 5, an inline project in `test.projects` that shares the Vite server of the config declaring it, Vitest's default, gets neither this file nor the plugin's defaults (jsdom, `exclude`, cleanup): set `sharedViteServer: false` in the root's `test` options.
- In `createTestApp()` tests, a failed query or mutation is tried as often as in the app, with no wait between the tries; retries used to be off. A query that fails once and then succeeds now shows its data, and an error shows once the last try has failed. A test that expects the error after the first request passes `defaultOptions: { queries: { retry: false } }`, the old behaviour, and `mutations: { retry: false }` where the app's `netjes({ query })` retries mutations. The app's `staleTime`, `retry`, refetch options and mutation `retry` now apply in its tests, and its `retryDelay` and its queries' `gcTime` do not. Seeded queries now stay fresh for the app's `staleTime`, counted from when `createTestApp()` is called, instead of one minute. With an app `staleTime` of 0, a component fetches its seeded query again as it mounts, as in the browser; with another one below a minute, only a component that mounts after that time, such as one rendered after the test moved fake timers on. Answer that request, or pass `defaultOptions: { queries: { staleTime: 60_000 } }`.
- Pages are no longer output-cached in the Development environment. Under `CachePage` or any other output caching, every request there renders the page, nothing is stored, and an output-cached page goes out `Cache-Control: no-store, private` unless it sets its own header. A stored page used to outlive every edit, and its markup and styles no longer matched the code, so React reported a hydration error ([ADR 0023](docs/decisions/0023-pages-are-not-output-cached-in-development.md)). Production and every other environment are unchanged, and `netjes routes` still lists `CachePage` pages as cached. A `WebApplicationFactory` test that checks page caching in the Development environment now sees every request render: run it with `UseEnvironment("Testing")` and `Netjes:Mode` set to `Development`. An app that kept `UseOutputCache()` out of Development can drop that guard; to keep data that is slow or costly to load from loading on every request there, cache it in the service that loads it (`IMemoryCache`, `HybridCache`). In Development the cookie warning now says that outside Development the render is stored, and `Netjes.Rendering.PageCachePolicy` logs once, at Information, that pages are not output-cached there.
- `X-Content-Type-Options: nosniff` now goes on every response that passes through `UseNetjes()`, not only on documents and images: client payloads, static files from `public/` and the client build, `robots.txt`, `sitemap.xml`, `/_netjes/antiforgery`, the app's own endpoints and answers from the output cache. A value the app sets itself is kept. A browser now refuses to run a script, or apply a stylesheet, served with no `Content-Type` or with one that is not a JavaScript type or `text/css`, and no longer takes a response with no `Content-Type` for HTML: it shows the markup as plain text and runs none of its scripts. Serve such responses with the right type; an endpoint that writes a page itself with `Response.WriteAsync` sets `Response.ContentType = "text/html; charset=utf-8"` first. Responses that middleware registered before `UseNetjes()` writes itself still go without it. `Netjes:SecurityHeaders:Enabled` set to false turns it off, and the image endpoint keeps its own `nosniff` either way ([ADR 0030](docs/decisions/0030-security-headers-beyond-documents.md)).
- With `frame-ancestors` in the Content-Security-Policy that goes out, documents now carry the `X-Frame-Options` it implies: `DENY` for `'none'`, an empty list or other sites only, and `SAMEORIGIN` when the list holds `'self'`, `*` or a scheme source such as `https:`. They used to carry none, or antiforgery's `SAMEORIGIN` on a visitor's first page. Every policy counts, several joined by commas included, and the strictest decides; a report-only policy does not count. A partner site named in `frame-ancestors` can no longer frame the app in a browser that knows only `X-Frame-Options`. An app that wants another value sends its own `X-Frame-Options`, which Netjes keeps. An app whose code stores antiforgery tokens before a page renders (`IAntiforgery.GetAndStoreTokens` in a loader or a middleware) still gets antiforgery's `SAMEORIGIN` on a first visit: set `AntiforgeryOptions.SuppressXFrameOptionsHeader = true` to get the one the policy implies ([ADR 0030](docs/decisions/0030-security-headers-beyond-documents.md)).
- In production, a sidecar script of the app's own (`Netjes:SidecarScript`) must answer `GET /health`, with any status and without reading a request body. Netjes now sends that request to a Node process that has answered no render for 5 seconds, and kills and restarts a process that sends nothing back within `RenderTimeout`, never less than 5 seconds. The sidecar Netjes ships has always answered it, so an app that uses it has nothing to change. A script that exits on the request, as one that reads every request as a render can, is restarted at every ping, and `Netjes.Sidecar.NodeSidecar` logs a warning that names `GET /health` and `Netjes:SidecarScript`.
- `CachePage` keeps its own copy of its tags, for the page's cache entries as for its `CachedPageMetadata`, so the two agree: changing the array after the call used to change the tags the entries got, and no longer does. An app that did that passes the tags it means to `CachePage` instead.
- React no longer compares the text directly in `<body>`, outside any element or `<Suspense>` boundary, in production as in development, since `<body>` now carries `suppressHydrationWarning` (see the entry on attributes under Fixed, [ADR 0026](docs/decisions/0026-netjes-html-and-body-skip-reacts-attribute-check.md)). When such text differs between the server and the browser, React used to report it (#418 in production) and render the page again in the browser; now it reports nothing, and the page keeps the server's text until that text changes. An app that renders text there that can differ, such as a time next to a layout's `{children}`, puts it in an element.
- `netjes --help` links the CLI reference at the release tag of the installed version (`https://github.com/DennisVerhoeven/netjes/blob/v<version>/docs/reference/cli.md`), not the page on `main`, which can describe commands and options that version does not have. The READMEs on npm and NuGet do the same from this release on: the release moves their links to the docs from `main` to its tag in the packages it publishes, and they link the security policy at `https://github.com/DennisVerhoeven/netjes/security/policy`, which always shows the current one ([ADR 0032](docs/decisions/0032-release-links-package-readmes-to-its-tag.md)). Apps have nothing to change.
- When a client navigation shows another page, the focus starts over at the top of the document, as after a page load: the next Tab goes to the first element that takes the focus. It used to stay on the link that was followed when that link was in a layout, and to fall back to `body` when the link went with the old page. The element a `#fragment` names now takes the focus, on the page on screen and on another, with `tabindex="-1"` until it loses the focus again when it takes none of its own; the router used to scroll to it only. The focus stays where it is after a navigation that changes only the query, `router.refresh()`, a form post that stays on its page and a modal that an intercepting route opens or Back closes; where the new page (`autoFocus`), the user or the app's code moved it while the navigation ran, a link's own `onClick` and a form's own `onSubmit` included; on a `scroll={false}` link that still has it; and in a field the user types into, such as a search box in a layout that navigates as the user types. No focus call scrolls, so the scroll position after a navigation is as before, the one Back restores included ([Focus and announcements](docs/guides/routing.md#focus-and-announcements), [ADR 0033](docs/decisions/0033-client-navigations-announce-the-page-and-start-the-focus-over.md)). Remove code of the app's own that focuses a fragment's element after a navigation. An end-to-end test that types right after a navigation to another page without focusing a field first now types into `body`: focus the field, as `locator.fill()` does. If a menu of the app closes in an effect after a navigation, let it give the focus back to its button only while the focus is still inside the menu; otherwise the button takes the focus from the top of the new page. Keyboard users now Tab through the header again after each navigation, so add a skip link (see Added). The promises of `router.push`, `router.replace` and `router.refresh()` resolve when they did before, once the router has handed the page to React, which can be before React shows it, as the docs now say ([ADR 0034](docs/decisions/0034-navigation-promises-resolve-when-react-has-the-page.md)): code that needs the new page runs in an effect.
- In the browser, zod now parses without compiled code. The client entry sets zod's `jitless` setting before any of the app's modules run, in every browser, with or without a Content-Security-Policy, and for every zod object schema made in the page: page and layout props, `api[...].response.parse(...)`, and the app's own search-param and form schemas ([zod in the browser](docs/guides/security.md#zod-in-the-browser), [ADR 0036](docs/decisions/0036-zod-runs-without-compiled-parsers-in-the-browser.md)). Parsing many objects with one schema is slower: a list of 1,000 small objects takes about 0.5 ms, against about 0.09 ms with compiled parsers. A new schema's first parse of one object, such as a page's props, is faster. Server rendering in the Node sidecar and the app's Vitest tests keep the compiled parsers, and Netjes has no setting to keep them in the browser. zod reads the setting from version 4.4.0 on, so an app on zod 4.0 to 4.3 upgrades zod to 4.4.0 or newer; an app made with `netjes new` asks for `^4.6.7` already. An app's own call of `z.compile(schema)` still makes a function from a string.
- A `GET` or `HEAD` for a page in another case of the literal segments its file names now answers 308 with the file's spelling: `/About` and `/ABOUT` go to `/about` for `app/about/page.tsx`, `/About/` to `/about/`, and `/ROBOTS.TXT` and `/Sitemap.xml` to `/robots.txt` and `/sitemap.xml`. A client navigation to such a URL gets a redirect payload, and the router shows the file's spelling. These URLs used to render the page as sent, so each was a page of its own to crawlers and to the output cache, and `<Link>` marked no link current on it. Only the literal segments change: route values (`/Blog/Hello` goes to `/blog/Hello`), the query string and the base path keep their case and encoding, and a trailing slash stays unless `TrailingSlash` is `Never`. Only the URL the client sent is redirected, and only to a page's spelling: a request that a rewrite or a re-execution changed (`UseRewriter`, `UseStatusCodePagesWithReExecute`, `UseExceptionHandler`, the page rendered for a failed form post) is answered as before, and so are requests with other methods, the app's own endpoints, the not-found page and every request on TestServer, which passes on no request target, so `WebApplicationFactory` tests still get the page. The redirect comes at the end of `UseNetjes()`, ahead of authentication and the output cache, so the output cache stores no other case that a browser sends. A request target that browsers do not send, with `.` or `..` segments (`/./About`) or in absolute form (`GET http://example.com/About`), is answered, and can be stored, as before. Browsers keep a 308: after a folder is renamed to another case, a visitor whose browser followed the old redirect is sent round in a loop until the browser forgets it. An app that serves pages at mixed-case URLs on purpose sets `NetjesOptions.RedirectLiteralCase = false` (`Netjes:RedirectLiteralCase=false`), which answers every case as before. A loader that redirected to its own spelling of a literal can drop that check. A test on Kestrel or in a browser that requests a page in another case now gets the 308 ([One URL per page](docs/guides/routing.md#one-url-per-page), [ADR 0039](docs/decisions/0039-a-page-url-has-one-spelling.md)).
- `isRouteHref`, and with it the generated `isHref()` and `Href` schema, refuses a URL that holds an ASCII control character (U+0000 to U+001F, or U+007F) or that starts or ends with a space. Browsers drop tabs and newlines anywhere in a URL, and control characters and spaces at either end, so `/\t/evil.example`, which `isRouteHref` took for a path where a root catch-all or two dynamic segments match, went to `evil.example`. A URL from data that holds such a character now fails `Href.parse`, and `isHref` returns false for it: trim it, or take the character out, before it is checked. Other URLs are checked as before.
- Netjes has a public type named `Href`, in the `Netjes` namespace, which the package's build targets import into every C# file of an app with implicit usings. A file that also imports another namespace with a type named `Href`, the app's own or a library's, now gets error CS0104 (an ambiguous reference) where it names `Href`: qualify the name, or give one of the two an alias (`using CmsHref = MyCms.Href;`). A type named `Href` in the namespace the file declares, or in one around it, is not ambiguous and is still the one the file gets.
- The docs index ([`docs/README.md`](docs/README.md)) lists the guides in the order an app is built, in four groups with a heading each: Build (Routing, Data loading, Actions and forms), Render (Rendering and streaming, Caching, Images), Publish (Metadata, Static export, Redirects, rewrites and headers) and Run (Security, Testing, Deployment, Coding agents). They were one list, in which Images came after Metadata, Deployment before Testing and Redirects, rewrites and headers after Testing. `llms.txt` and `llms-full.txt` list the guides in the new order, and so do the documentation table in the README, the React API reference and the agent skill's pointer to the guides. The guides themselves are unchanged, and apps have nothing to do. A site or a tool that builds a navigation from the index now finds four `###` headings under `## Guides`, each followed by its guides as bullets, where the bullets sat directly under `## Guides`.
- The export of an app that maps `MapSitemap` or `MapRobotsTxt` and falls back to a localhost site URL when none is configured, as the docs' example does, now publishes links to localhost in `sitemap.xml` and `robots.txt`. The export writes them and logs a warning for each in `Netjes.Export.StaticExportService`, and its exit code is unchanged. Set the static host's URL for the export, such as `SiteUrl=https://www.example.com npx netjes export` when the app reads `app.Configuration["SiteUrl"]`, or leave both files out with `.ExcludeFromExport()` ([static export](docs/guides/static-export.md#sitemap-and-robotstxt)).
- `netjes export` fails before it writes anything when a `robots.txt` or `sitemap.xml` in `public/`, or one a Vite plugin writes into the client build, has the path of `MapRobotsTxt` or `MapSitemap`: the app serves that file ahead of routing, so the endpoint never answered, and the export used to copy the file. Remove the file or the Map call, or keep the file and add `.ExcludeFromExport()` to the Map call. A page that needs a folder where the export writes a file, such as a page at `/404.html`, also fails the export now, naming both. The export's last line now reads `Exported N pages and M files to <dir>` ([static export](docs/guides/static-export.md#sitemap-and-robotstxt)).

### Fixed

- `<Link>` sets `aria-current="page"` only on a link to the page on screen ([ADR 0024](docs/decisions/0024-link-marks-the-current-page-by-path-and-query.md)). It used to compare the link's path alone, byte for byte. Now a link with a `#` (`/#features`, `#top`) is never marked; a link with a query is marked only while the page has the same values for every parameter the link names, in any order (`/search?q=other` is no longer marked on `/search?q=cache`); `/x` and `/x/` count as one page; and a link whose `href` already starts with the base path is marked on its page. Parameters a link leaves out still do not count, so a link that names fewer of them than the page is still marked, such as an "All" filter (`/blog`) on `/blog?tag=react`, or a `?page=2` link that drops the page's filter: set `aria-current` on such links yourself (`aria-current={undefined}` leaves it off). Check how filter and tab bars that style `aria-current` look, since which of their links are marked can change. Links with neither a `#` nor a query are marked as before, and now also when the page's path differs from theirs by a trailing slash. The [routing guide](docs/guides/routing.md#the-current-section) shows how to mark a section link, such as Docs on every page under `/docs`, with `aria-current="true"`.
- A `title.default` on a layout below the root, or on a page, now goes through the nearest `title.template` of the layouts above it, as [the metadata guide](docs/guides/metadata.md#titles) says and Next.js does. It skipped the templates before: below a root template of `'%s · Site'`, a docs layout's `default: 'Docs'` gave the title `Docs`, and it now gives `Docs · Site` (never `Docs · Docs · Site`, since a default does not go through the template next to it). A page's `title: { default: 'Intro' }` goes through the template in the same way, and so do the Open Graph and Twitter titles that fall back to the page's title. An app whose titles change this way and that wants them bare sets `title: { absolute: 'Docs' }` on that layout or page, which skips every template. A `default` on the root layout, and a title with no template above it, are unchanged.
- In development, a script that sets an attribute on `<html>` or `<body>` before the page hydrates, such as a theme script, a browser extension or a translator, no longer makes React log a hydration error. Netjes renders both elements and an app's layout cannot reach them, so both now carry `suppressHydrationWarning`, which ends React's attribute check for their own attributes ([ADR 0026](docs/decisions/0026-netjes-html-and-body-skip-reacts-attribute-check.md)). The markup the server sends is the same, and React does not check attributes in production. A mismatch in the head, or in any element in the body, is still reported; a different `lang` on `<html>` is not. The prop also changes what React compares in production: see the entry on text directly in `<body>` under Changed.
- `/robots.txt`, `/sitemap.xml`, `/_netjes/image` and the locale redirect at `/` answer `HEAD` as they answer `GET`, with the same status and headers and without the body. They answered `GET` only, so a `HEAD`, which crawlers and link checkers send, went to whatever else matched the URL: for `/robots.txt` and `/sitemap.xml` an empty 404, or a dynamic page at the root (`app/[lang]/page.tsx` answered with its not-found page); for the image endpoint and the redirect, the not-found page. An app that answered such a `HEAD` itself, with an endpoint of its own for `HEAD` at one of these URLs next to Netjes's, now gets 500 for it: both endpoints take `HEAD` there, with the same order and route precedence, so ASP.NET Core cannot choose between them (`AmbiguousMatchException`). Remove that endpoint; other apps have nothing to change. `netjes routes` now lists a `HEAD` row next to the `GET` row of each. Under output caching, a `HEAD` for an image is stored apart from the `GET`, so the first `HEAD` processes the image once more. `/_netjes/antiforgery` still answers `GET` only, and so does an endpoint an app maps with `MapGet`: map it with `MapMethods(pattern, [HttpMethods.Get, HttpMethods.Head], handler)` to answer `HEAD` too ([HEAD requests](docs/guides/routing.md#head-requests)).
- A Node process that stops answering without exiting (stuck in a loop, deadlocked, stopped by a signal) is now restarted, as one that crashed is. It used to stay ready: every server-rendered page waited out `RenderTimeout`, and its error page as long again, before a plain 500 went out; `/healthz` answered Healthy; and the client-rendered fallback never stepped in. In production Netjes now pings a process that has answered no render for 5 seconds, on a loopback connection of its own rather than through the HTTP client, so a ping records no HTTP client span or metric, and kills and restarts a process that sends nothing back within `RenderTimeout`, never less than 5 seconds ([ADR 0031](docs/decisions/0031-a-sidecar-that-stops-answering-is-restarted.md)). From the moment the process is taken out, `/healthz` reports Unhealthy (Degraded while other processes are ready), documents get the client-rendered fallback while no process is ready, and `Netjes.Sidecar.NodeSidecar` logs an error. Development is unchanged. Apps have nothing to do: a restart policy that acts when the container exits, as the template's `restart: always` does, is all a host needs. A synchronous render that holds a process for longer than `RenderTimeout`, which fails at that time limit as before, can now get the process restarted as well.
- `netjes export` with an output folder outside the app now exits 1 at once, with one line that names the folder and the app, and builds nothing. It used to build first (the types, both Vite bundles and a Release compile) and start the app with its Node sidecar, and only then did the app refuse the folder. The CLI compares the paths as .NET does, ignoring letter case on macOS and Windows. On macOS and Linux it takes the app's folder by its real path, with any symlink resolved, as the app sees its own folder, and resolves a relative output folder against it, with or without `--no-build`, so `out` now exports when `--cwd` names the app through a symlink, where the app used to refuse it. `netjes export --no-build` still leaves the check to the app, against `Netjes:Root`. A script that passes a folder outside the app now fails before the build: pass a folder inside the app, such as `out`.
- `netjes export` takes an output folder whose name starts with two dots, such as `..site`, as a folder inside the app; it used to refuse it as outside the app. For the same reason, such a folder inside one the app needs, such as `app/..site`, was not seen to overlap it, and the export wrote into it: it is now refused like any other folder there. `netjes new ..shop` now shows the new app's folder as `..shop` rather than by its absolute path. Apps have nothing to change.
- In development, the CSS that the sidecar inlines into a document, as `<style data-vite-dev-id>` elements, is now the browser's build of each file, made by Vite's client environment, and no longer a second build from Vite's SSR environment. When the two differed, Vite's client replaced the text before the page hydrated, and React logged a hydration error for the `<style>` ("A tree hydrated but some attributes of the server rendered HTML didn't match the client properties"). With `css.devSourcemap` on, that happened on every page that imports CSS, since only the browser's build carries the source map comment; it could also happen with a plugin that builds a file differently in each environment, as Tailwind CSS can after many edits. React also no longer compares the text of these elements, which Vite's client owns once it runs, so a file edited between the render and the import logs nothing either ([ADR 0035](docs/decisions/0035-development-styles-are-inlined-from-the-client-build.md)). Apps have nothing to change, and production, which links the built stylesheets, is unchanged. Should a Vite version write the module it serves for a CSS file in development in a form Netjes does not read, the sidecar inlines the SSR build as before and logs one warning, which names the first such file.
- A page under a Content-Security-Policy whose `script-src` leaves out `'unsafe-eval'`, such as the nonce-based and hash-based policies the [security guide](docs/guides/security.md#content-security-policy) shows, or that has no `script-src` and a `default-src` without it, no longer reports a violation as it loads. The first time a page module made a zod object schema, zod tested whether it may make a function from a string, the policy refused it, and the browser reported a `script-src` violation (blocked URI `eval`) on every document: a `securitypolicyviolation` event, and a report to the policy's `report-uri` or `report-to` endpoint when it has one. zod caught the error and the page worked. Chromium logged nothing to the console when the policy had a `script-src`; when the policy left scripts to `default-src`, Chromium logged one error on every document, which read in full "Note that 'script-src' was not explicitly set, so 'default-src' is used as a fallback." With zod 4.4.0 or newer, zod no longer makes that test in the browser, since it parses there without compiled code (under Changed). An app that turned zod's compiled parsers off itself to avoid the report, for example with a build hook that sets `jitless` in the chunks that hold zod, can remove that.
- A container of the template's production image now stops when the app crashes. The image started `dotnet <App>.dll` as the container's first process, PID 1, and the kernel ignores a signal that a container's PID 1 has no handler for, so when .NET aborted the process after a crash (an exception that nothing catches, `Environment.FailFast`, a stack overflow), the process did not end. On arm64 the thread that crashed spun at 100% of a CPU and the process never exited, so the container stayed up and `restart: always` never restarted it. After a crash at startup the container was unhealthy, but after a later one, such as on a thread of the app's own, the rest of the app kept serving and its health check still passed. On x86-64 it exited, but with another code than 134 (139 under emulation). The image now starts the app with `tini -s -- dotnet <App>.dll`: tini, from Ubuntu's package, is PID 1 and passes the signals it gets on to the app, so `docker stop` still stops it at once, and it exits with the app's code, so a crash ends the container with 134 ([a crash in a container](docs/guides/deployment.md#a-crash-in-a-container), [ADR 0042](docs/decisions/0042-the-apps-image-runs-an-init-as-pid-1.md)). Netjes's own startup failures still exit with code 1, and monitoring that expects 1 for every failed start now sees 134 for the other exceptions. Building the image needs Ubuntu's package archive for the new `tini` stage. An app made before this release copies three things from the template's `Dockerfile`: the `tini` stage (`FROM ${SDK_IMAGE} AS tini` and its `RUN apt-get ...` line), `COPY --from=tini /usr/bin/tini-static /usr/bin/tini` in the `production` stage, and the `ENTRYPOINT`, with its own dll name; or it runs its container under an init of the host's, such as `docker run --init` or `init: true` in Compose. The Blog's and TaskBoard's images run under tini as well.
- `llms.txt` lists `CONTRIBUTING.md` and `SECURITY.md`, which the docs index links. The generator named neither, and it listed a document it was not told about only when the document is under `docs/`, so both were missing from `llms.txt` and `llms-full.txt`. Both are under Optional, after the roadmap. `CONTRIBUTING.md` is in `llms.txt` only, marked as not in `llms-full.txt` as the architecture page is, and `SECURITY.md` is in `llms-full.txt` too: an agent that reads that file now also reads the security policy, with the address it gives for reporting a vulnerability. The generator now also lists any Markdown file in the repository that the docs index links and no entry names, under More, after the documents under `docs/` and in the order the index links them, so a page the index shows readers cannot be left out again; decision records stay out. Apps have nothing to change.

## [0.0.1] - 2026-10-30

Initial release.

### Added

- **Routing.** Pages in `app/` with the Next.js App Router conventions: `page`, `layout`, `template`, `loading`, `error`, `not-found`, `forbidden`, `unauthorized` and `global-error` files, route groups, private folders, dynamic, catch-all and optional catch-all segments, and parallel and intercepting routes. Each page is an ASP.NET Core endpoint, so the matcher, `RequireAuthorization()` and other endpoint conventions apply. Route warnings at startup and in `netjes routes` for loader parameters that miss a route value, for pages that match the same URLs, and for form inputs that refuse a post without a checkbox.
- **Client router.** `<Link>` with prefetching, `useRouter`, `usePathname`, `useSearchParams` and `useParams` with optional schemas, `useSelectedLayoutSegment(s)`, `useNavigation`, scroll restoration, and back and forward from memory for the last 50 pages. Base paths (`UsePathBase` with `netjes({ basePath })`) and locale routing on a `[lang]` segment (`AddNetjesLocalization`, `useLocale`).
- **Data loading.** C# page loaders (`MapPageLoader`) and layout loaders (`MapLayoutLoader`) that bind like minimal API handlers and return `Page.Props`, `NotFound`, `Forbidden`, `Unauthorized`, `Redirect` or `LocalRedirect`. Layout loaders are skipped on navigations within their section, keyed by signed segment keys. Shared props for every page (`UseSharedProps`), public configuration read at runtime (`Netjes:PublicConfig`, `usePublicConfig`), and a built-in TanStack Query client seeded from loaders with `.WithQuery`.
- **Generated types.** `generated/netjes.ts`, written from the app's System.Text.Json contracts: zod schemas for page and layout props, shared props, JSON endpoints and page action forms, typed server action references, typed routes (`route()`, `Href`), and `definePage` and `defineLayout` to parse props with them. `netjes generate --check` for CI.
- **Server actions and forms.** `MapAction` endpoints with typed references, `useAction` and `<Form>`, DataAnnotations and `IValidatableObject` validation, `ServerAction.Ok`, `Invalid`, `Redirect`, `Forbidden` and `NotFound`, revalidation of cached pages and refreshes, TanStack Query updates, and page actions (`MapPageAction`), whose inputs are validated the same way, with the errors in `usePageActionState`. Forms post without JavaScript and come back with their errors and the declared fields' values. Antiforgery and same-origin checks on every action, a 1 MB body limit for server actions, and a refresh of the router's memory and query cache, in every tab of the app, when an action signs someone in or out.
- **Rendering.** Server rendering in a pool of supervised Node processes (`SidecarProcesses`), restarted with backoff and reported by a health check. Streamed documents with `loading.tsx` and Suspense, `Page.Defer` for slow values (with an overload that runs the work in its own DI scope), ready boundaries written in place, complete documents for crawlers, and a document the browser renders itself when no Node process is ready in production. `dynamic()`, `clientOnly()`, error pages and built-in fallbacks.
- **Caching.** `.CachePage(duration, tags)` on ASP.NET Core output caching, with Netjes's keys under any output-cache policy; revalidation by tag or path from actions or through `IPageCache`; draft mode (`IDraftMode`, `useDraftMode`) that bypasses the cache. Pages that are not cached go out `no-store`.
- **Metadata, images and scripts.** The Metadata API on pages and layouts and `PageMetadata` from C#, `MapSitemap` and `MapRobotsTxt`, `<Script>` with three loading strategies, and `<Image>` with the `/_netjes/image` endpoint: configured widths and qualities, allow-listed remote hosts, bounded concurrency, and a pluggable `IImageProcessor`. `Netjes.Images.SkiaSharp` resizes and encodes WebP.
- **Static export.** `netjes export` writes every page as a complete HTML document, with `.StaticParams(...)` for dynamic pages and `.ExcludeFromExport()`, and refuses pages that need a server.
- **Security.** `X-Content-Type-Options`, `Referrer-Policy` and a same-origin framing policy on every document, an opt-in Content-Security-Policy with per-request nonces or hashes, redirects limited to relative and http(s) URLs, form fields that look like secrets never handed back, and a token on every request to the Node processes.
- **Operations.** The `Netjes` ActivitySource and Meter for OpenTelemetry (loader, action, render and sidecar spans and durations, web vitals with `netjes/vitals`), a health check, and support for several instances sharing an output-cache store.
- **Testing.** Vitest defaults in the Vite plugin and `createTestApp()` from `netjes/testing`, with a fake router, seeded queries and fake server actions.
- **Tooling.** The `netjes` command: `new`, `dev`, `build`, `start`, `generate`, `routes`, `export`, `info` and `agents`. An app template with a C# loader, a validated server action, component tests, Tailwind CSS and Docker files for development and production. `AGENTS.md`, `CLAUDE.md` and a Netjes skill for coding agents in new apps, and `llms.txt` and `llms-full.txt` for the docs. The npm package ships compiled ES modules with type declarations.
