# Changelog

All notable changes to Netjes are recorded here: the `netjes` npm package and the `Netjes` and `Netjes.Images.SkiaSharp` NuGet packages, which are released together under one version. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and versions follow [Semantic Versioning](https://semver.org/spec/v2.0.0.html). Before 1.0, a new version can change the API; its entry says what to do.

## [Unreleased]

### Added

- `<Link>`, `<Form>`, `<SubmitButton>` and `<Image>` take a `ref` to the element they render. `LinkProps`, `FormProps`, `SubmitButtonProps` and `ImageProps` now start from React's `ComponentPropsWithRef` instead of the `*HTMLAttributes` types, which left the ref out, so `<Link ref={ref}>` is no longer a type error. The ref already reached the element at runtime, and only the types refused it; an app that worked around the type error, for example with `document.getElementById(id)`, can pass the ref instead. The four types also include `key` now; React handles it, as for any element, and never passes it to the component.
- Once the client router runs in a document, `<html>` carries `data-netjes-hydrated=""`: the sign that the page has hydrated, which end-to-end tests wait for before they click, with `await expect(page.locator('html')).toHaveAttribute('data-netjes-hydrated', '')` ([testing](docs/guides/testing.md#wait-for-hydration), [ADR 0025](docs/decisions/0025-a-mark-on-html-says-the-client-router-runs.md)). It appears after the router has registered as the page's action client, on hydrated pages and on pages rendered in the browser when no sidecar was ready, and the server never renders it. A test helper that waited for the router's key in `history.state` should wait for the attribute instead: the browser keeps that state when it loads the document again, so after a reload the key is there before any of the page's scripts has run. The name is reserved, and a stylesheet or a DOM snapshot that reads `<html>`'s attributes in the browser now sees one more.
- Testing Library works with Vitest's fake timers. Under `vi.useFakeTimers()`, `waitFor`, `findBy…` and user-event never returned, because Testing Library moves fake timers on only through Jest's `jest` global. Netjes's setup file now defines that global while Vitest's timers are fake, and leaves it undefined with real timers ([ADR 0027](docs/decisions/0027-testing-library-advances-vitest-fake-timers.md)). `waitFor` and `findBy…` move the fake clock on as they wait, and their timeout counts fake time; create user-event's user with `userEvent.setup({ advanceTimers: vi.advanceTimersByTime })`. While timers are fake, `typeof jest` is `'object'`, so a library that looks for Jest finds it then, and a test on `vi.useFakeTimers({ shouldAdvanceTime: true })` takes Testing Library's path for fake timers. A `jest` global the app's own setup file defines, or a test assigns, is kept.
- `createTestApp()` starts from the app's `netjes({ query })` defaults. `netjes()` sets Vitest's `test.provide['netjes:query']` to the `query` option's `defaultOptions` (`{}` when there are none, nothing with `query: false`), next to the app's own `provide` keys, and Netjes's setup file hands them to the harness ([ADR 0028](docs/decisions/0028-test-harness-starts-from-the-apps-query-defaults.md)).
- A route warning for an endpoint of the app that ties with a page or a page action. Such an endpoint ranks the same as the page in ASP.NET Core's matcher: it has an HTTP method in common with it, the same order, route precedence and literals, a host in common or no host on either, and accepted content types listed by both or by neither (two endpoints that both list content types tie for a request without one, such as a POST without a body). ASP.NET Core cannot choose between the two and answers each request that both match with 500 (`AmbiguousMatchException`), as it did before. Now the app also logs a warning at startup, in the category `Netjes.Routing.RouteDiagnostics`, and `netjes routes` lists it (the kind `ambiguous-endpoint` in `--json`), naming the endpoint's methods and route and the page file. Netjes's own `MapLocaleRedirect()` next to an `app/page.tsx` is one such endpoint. Give the endpoint `.WithOrder(-1)` if it should answer those URLs, or change its route. An app that keeps the tie, or whose own matcher policies tell the two endpoints apart, can raise the category's log level, which hides every route warning ([ADR 0029](docs/decisions/0029-an-endpoint-that-ties-with-a-page-is-a-route-warning.md)). The routing guide has a new section, [Endpoints next to pages](docs/guides/routing.md#endpoints-next-to-pages), on which endpoint answers a URL and how to link to a file next to a page.
- `PageRouteMetadata` and `CachedPageMetadata` in `Netjes.Routing`, so app code and tests can find the app's pages by walking `EndpointDataSource`, as `netjes routes` does ([endpoint metadata](docs/reference/csharp-api.md#endpoint-metadata)). Every endpoint that serves a page carries `PageRouteMetadata`, with the page's `Pattern` as its file names it and `IsLoader`, true on the endpoint `MapPageLoader` maps. Every endpoint `CachePage` is put on carries `CachedPageMetadata`, with the `Duration` and `Tags` it was given. `CachePage` now keeps its own copy of the tags, for the page's cache entries as for the metadata, so the two agree: changing the array after the call used to change the tags the entries got, and no longer does. An app that did that passes the tags it means to `CachePage` instead. Otherwise this is new API only, and nothing else changes at runtime. Code that finds a page's endpoint by its display name (`Page /blog/[slug]`), which is not part of the API, can read `PageRouteMetadata` instead.
- `route()` and `buildHref` take a fourth argument, `{ hash }`, which adds a `#fragment` after the query: `route('/docs/[...path]', { path: ['guides', 'caching'] }, undefined, { hash: 'keys' })` is `/docs/guides/caching#keys`. The hash is the id of an element on the page. One leading `#` is dropped and the rest is percent-encoded (`'über-uns'` becomes `#%C3%BCber-uns`, which browsers and the router decode when they look for the element); with nothing left, no fragment is added. The third argument is still the query, so a link with a fragment and no query passes `undefined` there ([routing guide](docs/guides/routing.md#links)). The generated `route()` has a new signature, so run `npx netjes generate` after upgrading, or start the app in Development, and commit `generated/netjes.ts`: `npx netjes generate --check` in CI fails until you do. Until then `route()` keeps its old signature and takes no `hash`. A link whose fragment you write into the string yourself needs no change.

### Changed

- `netjes()` adds a setup file of its own to every app's Vitest `setupFiles`, after the app's own setup files, also when the app sets `setupFiles` itself, `[]` included. The cleanup file (`netjes/testing/setup`) is still added only when the app sets none. An app that set `setupFiles: []` to keep Netjes's setup files out now gets the new one; `netjes({ test: false })` still leaves out every Vitest setting the plugin adds, this file included. Under Vitest 5, an inline project in `test.projects` that shares the Vite server of the config declaring it, Vitest's default, gets neither this file nor the plugin's defaults (jsdom, `exclude`, cleanup): set `sharedViteServer: false` in the root's `test` options.
- In `createTestApp()` tests, a failed query or mutation is tried as often as in the app, with no wait between the tries; retries used to be off. A query that fails once and then succeeds now shows its data, and an error shows once the last try has failed. A test that expects the error after the first request passes `defaultOptions: { queries: { retry: false } }`, the old behaviour, and `mutations: { retry: false }` where the app's `netjes({ query })` retries mutations. The app's `staleTime`, `retry`, refetch options and mutation `retry` now apply in its tests, and its `retryDelay` and its queries' `gcTime` do not. Seeded queries now stay fresh for the app's `staleTime`, counted from when `createTestApp()` is called, instead of one minute. With an app `staleTime` of 0, a component fetches its seeded query again as it mounts, as in the browser; with another one below a minute, only a component that mounts after that time, such as one rendered after the test moved fake timers on. Answer that request, or pass `defaultOptions: { queries: { staleTime: 60_000 } }`.
- Pages are no longer output-cached in the Development environment. Under `CachePage` or any other output caching, every request there renders the page, nothing is stored, and an output-cached page goes out `Cache-Control: no-store, private` unless it sets its own header. A stored page used to outlive every edit, and its markup and styles no longer matched the code, so React reported a hydration error ([ADR 0023](docs/decisions/0023-pages-are-not-output-cached-in-development.md)). Production and every other environment are unchanged, and `netjes routes` still lists `CachePage` pages as cached. A `WebApplicationFactory` test that checks page caching in the Development environment now sees every request render: run it with `UseEnvironment("Testing")` and `Netjes:Mode` set to `Development`. An app that kept `UseOutputCache()` out of Development can drop that guard, and caches data that is slow or costly to load in the service that loads it (`IMemoryCache`, `HybridCache`). In Development the cookie warning now says that outside Development the render is stored, and `Netjes.Rendering.PageCachePolicy` logs once, at Information, that pages are not output-cached there.

### Fixed

- `<Link>` sets `aria-current="page"` only on a link to the page on screen ([ADR 0024](docs/decisions/0024-link-marks-the-current-page-by-path-and-query.md)). It used to compare the link's path alone, byte for byte. Now a link with a `#` (`/#features`, `#top`) is never marked; a link with a query is marked only while the page has the same values for every parameter the link names, in any order (`/search?q=other` is no longer marked on `/search?q=cache`); `/x` and `/x/` count as one page; and a link whose `href` already starts with the base path is marked on its page. Parameters a link leaves out still do not count, so a link that names fewer of them than the page is still marked, such as an "All" filter (`/blog`) on `/blog?tag=react`, or a `?page=2` link that drops the page's filter: set `aria-current` on such links yourself (`aria-current={undefined}` leaves it off). Check how filter and tab bars that style `aria-current` look, since which of their links are marked can change. Links with neither a `#` nor a query are marked as before, and now also when the page's path differs from theirs by a trailing slash. The [routing guide](docs/guides/routing.md#the-current-section) shows how to mark a section link, such as Docs on every page under `/docs`, with `aria-current="true"`.
- A `title.default` on a layout below the root, or on a page, now goes through the nearest `title.template` of the layouts above it, as [the metadata guide](docs/guides/metadata.md#titles) says and Next.js does. It skipped the templates before: below a root template of `'%s · Site'`, a docs layout's `default: 'Docs'` gave the title `Docs`, and it now gives `Docs · Site` (never `Docs · Docs · Site`, since a default does not go through the template next to it). A page's `title: { default: 'Intro' }` goes through the template in the same way, and so do the Open Graph and Twitter titles that fall back to the page's title. An app whose titles change this way and that wants them bare sets `title: { absolute: 'Docs' }` on that layout or page, which skips every template. A `default` on the root layout, and a title with no template above it, are unchanged.
- In development, a script that sets an attribute on `<html>` or `<body>` before the page hydrates, such as a theme script, a browser extension or a translator, no longer makes React log a hydration error. Netjes renders both elements and an app's layout cannot reach them, so both now carry `suppressHydrationWarning`, which ends React's attribute check for their own attributes ([ADR 0026](docs/decisions/0026-netjes-html-and-body-skip-reacts-attribute-check.md)). The markup the server sends is the same, and React does not check attributes in production. The prop also stops React from comparing the text directly in `<body>`, outside any element or `<Suspense>` boundary, in production as well: when such text differs between the server and the browser, React used to report it (#418 in production) and render the page again in the browser, and now it reports nothing and the page keeps the server's text until that text changes. An app that renders text there that can differ, such as a time next to a layout's `{children}`, puts it in an element. A mismatch in the head, or in any element in the body, is still reported; a different `lang` on `<html>` is not.
- `/robots.txt`, `/sitemap.xml`, `/_netjes/image` and the locale redirect at `/` answer `HEAD` as they answer `GET`, with the same status and headers and without the body. They answered `GET` only, so a `HEAD`, which crawlers and link checkers send, went to whatever else matched the URL: for `/robots.txt` and `/sitemap.xml` an empty 404, or a dynamic page at the root (`app/[lang]/page.tsx` answered with its not-found page); for the image endpoint and the redirect, the not-found page. An app that answered such a `HEAD` itself, with an endpoint of its own for `HEAD` at one of these URLs next to Netjes's, now gets 500 for it: both endpoints take `HEAD` there, with the same order and route precedence, so ASP.NET Core cannot choose between them (`AmbiguousMatchException`). Remove that endpoint; other apps have nothing to change. `netjes routes` now lists a `HEAD` row next to the `GET` row of each. Under output caching, a `HEAD` for an image is stored apart from the `GET`, so the first `HEAD` processes the image once more. `/_netjes/antiforgery` still answers `GET` only, and so does an endpoint an app maps with `MapGet`: map it with `MapMethods(pattern, [HttpMethods.Get, HttpMethods.Head], handler)` to answer `HEAD` too ([HEAD requests](docs/guides/routing.md#head-requests)).

## [0.0.2] - 2026-11-03

### Fixed

- A page could show twice. When the client entry came from the browser's cache, it could hydrate a streamed document before the shell had been parsed; React reported a hydration error (#418), rendered the page itself, and the rest of the server's HTML followed it. The client entry now waits for the end of the shell ([ADR 0022](docs/decisions/0022-hydrate-once-the-shell-is-parsed.md)). Every server-rendered document ends its body with an empty `<template id="__NETJES_SHELL_END__">`. Apps have nothing to change, but a stylesheet that targets the body's last child now matches it.

## [0.0.1] - 2026-10-30

Initial release.

### Added

- **Routing.** Pages in `app/` with the Next.js App Router conventions: `page`, `layout`, `template`, `loading`, `error`, `not-found`, `forbidden`, `unauthorized` and `global-error` files, route groups, private folders, dynamic, catch-all and optional catch-all segments, and parallel and intercepting routes. Each page is an ASP.NET Core endpoint, so the matcher, `RequireAuthorization()` and other endpoint conventions apply. Route warnings at startup and in `netjes routes` for loader parameters that miss a route value, for pages that match the same URLs, and for form inputs that refuse a post without a checkbox.
- **Client router.** `<Link>` with prefetching, `useRouter`, `usePathname`, `useSearchParams` and `useParams` with optional schemas, `useSelectedLayoutSegment(s)`, `useNavigation`, scroll restoration, and back and forward from memory for the last 50 pages. Base paths (`UsePathBase` with `netjes({ basePath })`) and locale routing on a `[lang]` segment (`AddNetjesLocalization`, `useLocale`).
- **Data loading.** C# page loaders (`MapPageLoader`) and layout loaders (`MapLayoutLoader`) that bind like minimal API handlers and return `Page.Props`, `NotFound`, `Forbidden`, `Unauthorized`, `Redirect` or `LocalRedirect`. Layout loaders are skipped on navigations within their section, keyed by signed segment keys. Shared props for every page (`UseSharedProps`), public configuration read at runtime (`Netjes:PublicConfig`, `usePublicConfig`), and a built-in TanStack Query client seeded from loaders with `.WithQuery`.
- **Generated types.** `generated/netjes.ts`, written from the app's System.Text.Json contracts: zod schemas for page and layout props, shared props, JSON endpoints and page action forms, typed server action references, typed routes (`route()`, `Href`), and `definePage` and `defineLayout` to parse props with them. `netjes generate --check` for CI.
- **Server actions and forms.** `MapAction` endpoints with typed references, `useAction` and `<Form>`, DataAnnotations and `IValidatableObject` validation, `ServerAction.Ok`, `Invalid`, `Redirect`, `Forbidden` and `NotFound`, revalidation of cached pages and refreshes, TanStack Query updates, and page actions (`MapPageAction`), whose inputs are validated the same way, with the errors in `usePageActionState`. Forms post without JavaScript and come back with their errors and the declared fields' values. Antiforgery and same-origin checks on every action, a 1 MB body limit for server actions, and a refresh of the router's memory and query cache, in every tab of the app, when an action signs someone in or out.
- **Rendering.** Server rendering in a pool of supervised Node processes (`SidecarProcesses`), restarted with backoff and reported by a health check. Streamed documents with `loading.tsx` and Suspense, `Page.Defer` for slow values (with an overload that runs the work in its own DI scope), ready boundaries written in place, complete documents for crawlers, and a document the browser renders itself when no Node process is ready in production. `dynamic()`, `clientOnly()`, error pages and built-in fallbacks.
- **Caching.** `.CachePage(duration, tags)` on ASP.NET Core output caching, with Netjes's keys under any output-cache policy; revalidation by tag or path from actions or through `IPageCache`; draft mode (`IDraftMode`, `useDraftMode`) that bypasses the cache. Pages that are not cached go out `no-store`.
- **Metadata, images and scripts.** The Metadata API on pages and layouts and `PageMetadata` from C#, `MapSitemap` and `MapRobotsTxt`, `<Script>` with three loading strategies, and `<Image>` with the `/_netjes/image` endpoint: configured widths and qualities, allow-listed remote hosts, bounded concurrency, and a pluggable `IImageProcessor`. `Netjes.Images.SkiaSharp` resizes and encodes WebP.
- **Static export.** `netjes export` writes every page as a complete HTML document, with `.StaticParams(...)` for dynamic pages and `.ExcludeFromExport()`, and refuses pages that need a server.
- **Security.** `X-Content-Type-Options`, `Referrer-Policy` and a same-origin framing policy on every document, an opt-in Content-Security-Policy with per-request nonces or hashes, redirects limited to relative and http(s) URLs, form fields that look like secrets never handed back, and a token on every request to the Node processes.
- **Operations.** The `Netjes` ActivitySource and Meter for OpenTelemetry (loader, action, render and sidecar spans and durations, web vitals with `netjes/vitals`), a health check, and support for several instances sharing an output-cache store.
- **Testing.** Vitest defaults in the Vite plugin and `createTestApp()` from `netjes/testing`, with a fake router, seeded queries and fake server actions.
- **Tooling.** The `netjes` command: `new`, `dev`, `build`, `start`, `generate`, `routes`, `export`, `info` and `agents`. An app template with a C# loader, a validated server action, component tests, Tailwind CSS and Docker files for development and production. `AGENTS.md`, `CLAUDE.md` and a Netjes skill for coding agents in new apps, and `llms.txt` and `llms-full.txt` for the docs. The npm package ships compiled ES modules with type declarations.
