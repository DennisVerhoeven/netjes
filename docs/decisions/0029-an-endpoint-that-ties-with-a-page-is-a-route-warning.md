# 0029 – An endpoint that ties with a page is a route warning

Status: accepted; extends [ADR 0015](0015-route-warnings-name-what-is-likely-wrong.md)

## Context

Apps map their own endpoints next to their pages: an API, a file such as a Markdown copy of each docs page at `/docs/{**path:regex(\.md$)}` next to `app/docs/[...path]/page.tsx`, or Netjes's `MapLocaleRedirect()` for `/`. For a request, ASP.NET Core ranks the endpoints whose routes match the URL by order, then route precedence, then its matcher policies in turn: an endpoint that names HTTP methods ranks ahead of one that names none, then one that requires a host ahead of one that does not, then one that lists the content types it accepts ahead of one that takes every content type. Pages and page actions are endpoints of order 0. When an endpoint of the app ranks the same as a page and a request matches both, the matcher cannot choose and throws an `AmbiguousMatchException`, so the request answers 500. Nothing said so before that request: the route warnings compared pages with pages only ([ADR 0015](0015-route-warnings-name-what-is-likely-wrong.md)), and ASP.NET Core finds a tie only while it matches a request.

## Decision

- `RouteDiagnostics` compares the endpoints of each page, the one that answers GET and HEAD and the page action's POST, with every endpoint that is no page and names an HTTP method. Netjes's own endpoints count, since the locale redirect ties with `app/page.tsx`. The not-found fallback and the server actions carry Netjes's page marker without a page, and are left out. An endpoint that names no method ranks after one that does, so it never ties with a page.
- A pair is warned when the matcher ranks the two the same and a request can fit both: they have an HTTP method in common; the same order and the same route precedence, which means the same number of segments and the same kind of segment at each position; the same literal wherever both have one, in any case; a host in common, or no host on either; and accepted content types listed by both, or by neither. A parameter with a required value, as MVC gives a controller action's route, counts as that literal, because the matcher matches it as one. Hosts are compared as written: the host policy keeps two hosts that differ only in case apart, and sends each request to one of them. Content types are compared by whether an endpoint lists any: two that both do tie for a request without a Content-Type, such as a POST without a body, whatever they list, because the matcher then keeps every endpoint for the URL unless one of them takes every content type. Route constraints are not compared: a page's own are a catch-all's `minlength(1)` and those of a route group's prefix.
- The warning has the kind `ambiguous-endpoint`. It names the endpoint's methods and route, the page file or its action, and the page's URL, and says what to do: `.WithOrder(-1)` on the endpoint if it should answer those URLs, or another route.
- It is a warning like the others, logged at startup and listed by `netjes routes`, never a reason to stop, and hidden through the log level of `Netjes.Routing.RouteDiagnostics`.

## Alternatives considered

- **Fail startup.** Equal ranks only stand in for an ambiguity: an app's own matcher policies can still tell the two endpoints apart. Endpoints also come from libraries the app does not control. A false positive would stop a working app, which is why [ADR 0015](0015-route-warnings-name-what-is-likely-wrong.md) made route warnings warnings.
- **Warn about every endpoint that shares URLs with a page.** `.WithOrder(-1)`, or a literal route next to a dynamic page, is the intended way for an endpoint to take URLs from a page; most warnings would be about correct apps.
- **Ask the matcher about sample URLs.** Its candidate sets are internal to ASP.NET Core, and a sample URL would have to satisfy each endpoint's route constraints, such as regular expressions.
- **Reuse the check for overlapping pages.** It compares file patterns, which have no constraints, hosts, methods or content types: `/blog/{id:int}` next to `app/blog/[slug]/page.tsx` would be warned, though its constraint ranks the endpoint first.
- **Leave out endpoints with required values.** It would miss a real tie, such as the GET action `About` of a `HomeController` whose attribute route names the controller and the action as parameters, `[Route("{controller}/{action}")]`, next to `app/home/about/page.tsx`. MVC's conventional routes have an order above 0, so they rank after the pages.
- **Leave out page actions.** A `MapPost` next to a page action that binds no form input ties in the same way.
- **Compare accepted content types by a value in common, as hosts are.** Two endpoints that both list content types tie for a request without one, whatever they list, so a `MapPost` that takes JSON next to a page action that takes a form would not be warned, though a POST without a body answers 500.
- **Warn only when the hosts or accepted content types are the same sets.** Two host lists that share one value still tie for a request with that host. Two lists of content types tie even when they differ: for a request without a Content-Type, and for one with a type both accept, such as a multipart post to an endpoint that takes a file upload next to a page action that takes a form.
- **Have the generated `Href` type refuse the URLs an endpoint answers.** A TypeScript template literal type cannot leave out what a regular expression matches.

## Consequences

- An app with such a tie logs a warning on every start, and `netjes routes` lists it (`warnings` in `--json`). The requests it names answered 500 before and still do; routing is unchanged.
- Silencing is all or nothing, as for the other route warnings: raising the category's log level hides them all.
- Some warnings name endpoints that do not fail. The app's own matcher or endpoint selector policies (API versioning, for one) can tell two endpoints of one rank apart. Route constraints can leave no URL in common: an endpoint's constraint that allows nothing a page's catch-all matches, or one that a route group's constraint excludes, such as `/{org:alpha}/projects` next to a page mapped under `/{tenant:int}`. And two endpoints that list different content types fail only a request without a Content-Type, and none when a third endpoint for the URL takes every content type, such as the app's `MapFallback`, which then gets those requests.
- Some ties go unreported: hosts are compared as written, so one host written two ways (`www.example.com` and `www.example.com:*`), or a host wildcard next to one it covers (`*.example.com` and `*.shop.example.com`), which can tie, is missed; ties between two endpoints of the app are left to ASP.NET Core; and endpoints added after startup are not seen. A page that ranks ahead of an endpoint for all of its URLs is no tie either, so an endpoint that never answers is not reported: `MapHealthChecks("/healthz")`, which names no method, never answers GET next to `app/healthz/page.tsx`.
- Endpoints from libraries are checked too. `MapHealthChecks` names no method, and `MapOpenApi`'s route has a segment of two parts (`{documentName}.json`), which no page has, so neither ties with a page.
